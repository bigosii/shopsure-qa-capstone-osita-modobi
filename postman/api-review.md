# ShopSure API: payload and data-exposure review

**How this was done:** every row is based on what the API actually returned during testing (Postman collection and extra manual requests on 2026-11-16 and 2026-11-17), not on assumptions. Test accounts created during the review were deleted afterwards.

| Endpoint | Params sent | Is every param needed? Why? | Response fields that look over-exposed | Recommendation |
|---|---|---|---|---|
| `GET /api/productsList` | None | Yes. No input is needed to list products. | None sensitive. Each product returns `id`, `name`, `price`, `brand`, `category`. All 34 products come back in one response, with no paging. `price` is text (`"Rs. 500"`), not a number plus a currency. | Add paging (`page`, `limit`) so the response doesn't grow with the catalogue. Return `price` as a number with a separate `currency` field. |
| `GET /api/brandsList` | None | Yes. No input is needed to list brands. | None sensitive. But it returns 34 entries for only 8 distinct brands (one entry per product, for example "Polo" ×6), which is redundant data. | Return each brand once, with a unique `id` per brand. |
| `POST /api/searchProduct` | `search_product` | Yes. It's the search term. | None sensitive (the same product fields as productsList). An empty term returns all products. | Since search only reads data, use `GET` with a query parameter. Reject an empty term with a 400. |
| `POST /api/createAccount` | 17: `name`, `email`, `password`, `title`, `birth_date`, `birth_month`, `birth_year`, `firstname`, `lastname`, `company`, `address1`, `address2`, `country`, `zipcode`, `state`, `city`, `mobile_number` | **No.** Removing one field at a time showed the API requires 11 (`name`, `email`, `password`, `firstname`, `lastname`, `address1`, `country`, `zipcode`, `state`, `city`, `mobile_number`); the other 6 are optional. Even so, an account only really needs `email`, `password` and a name: address and phone belong at checkout. `name` also overlaps with `firstname` + `lastname`. | The response is only a message (good). But the request collects personal data (date of birth, phone, full address) that isn't needed to register. | Cut signup to `email`, `password` and `name`; collect address and phone at checkout. Validate values: the API accepted an invalid email (`notanemail`), a country not in the website's list, and empty values for required fields. Use the same field names as getUserDetailByEmail (`birth_date` vs `birth_day`, `firstname` vs `first_name`). |
| `POST /api/verifyLogin` | `email`, `password` | Yes. Both are needed to check a login. | None. It returns only a message. | Return a session token on success, so later calls (update, delete, user details) can be authorised by token instead of resending the password. Use 401 for wrong credentials. Say which field is missing in the error. |
| `GET /api/getUserDetailByEmail` | `email` (query parameter) | The email identifies the user, but **no password or token is asked for**, so anyone who knows (or guesses) an email can call it. | **Yes, the most over-exposed endpoint.** It returns `id`, `name`, `email`, `title`, `birth_day`, `birth_month`, `birth_year`, `first_name`, `last_name`, `company`, `address1`, `address2`, `country`, `state`, `city`, `zipcode` to anyone. The `id` is an internal database number (seen around 3,240,000), which hints at how many accounts exist. The password and phone number are not returned (good). | Require authentication, and only return the caller's own details (for example `GET /api/me` with a token). Remove `id` and the date of birth from the response. Don't put an email in the URL: URLs end up in server logs and browser history. |
| `PUT /api/updateAccount` | The same 17 fields as createAccount (we sent all of them, with a new `name` and `city`) | **No.** We only changed 2 fields but had to send all 17. A request without `password` is rejected, so the password is resent on every update. | None. It returns only a message. | Allow partial updates (`PATCH` with only the changed fields), authorised by a token rather than the password. A wrong password returns `404 "Account not found!"`; it should be 401 with a clear message. |
| `DELETE /api/deleteAccount` | `email`, `password` | Yes. Asking for the password before a delete is a good safeguard. | None. It returns only a message. | A wrong password returns `404 "Account not found!"`; return 401 instead, so it doesn't look like the account is missing. Consider a confirmation step or soft delete, since deletion can't be undone. |

## Summary

- **Biggest risk:** `getUserDetailByEmail` shares personal data (name, date of birth, full address) with anyone, with no password or token. This is Finding 1 (High) in the README.
- **Too much data collected:** signup asks for 17 fields where 3 would do, and it doesn't validate them (invalid email, unlisted country, empty required values).
- **No sessions:** the API never issues a token, so the password has to be sent again for every update and delete.
- **Inconsistent errors:** errors come back as HTTP 200, a wrong password is reported as "Account not found!", and some messages don't name the missing field.
